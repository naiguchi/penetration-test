# ペネトレーションテスト（マルチテナント）

## 契約

- 手順と報告形式の正本。実行は `agt-penetration-test`。
- 入力（範囲・環境・diff）に対し、成立するベクターを証拠付きで列挙する。
- 修正実装はユーザーが明示したときだけ。ベース URL の無い環境へはリクエストしない。

想定する開発環境は、NestJS on Lambda、API Gateway、Cognito、Prisma + Aurora PostgreSQL、React、S3 である。テナント所有の行はテナントキーを持つ。ロール権限と行の所有テナントは別判定である。対象リポジトリの構成が違えば、リポジトリ側を優先する。

## 倫理・スコープ

| 許可 | 禁止 |
| --- | --- |
| リポジトリ内の静的解析 | その依頼でベース URL が無い環境へのリクエスト |
| ユーザーがベース URL を書いた開発環境への最小リクエスト | 本番へのリクエスト。ユーザーが本番 URL を明示した場合も、破壊・大量送信はしない |
| 報告の中の最小再現（トークンは `<REDACTED>`）。秘密のコミット禁止 | `.env`・鍵・トークンの書き込み |
| ユーザー依頼時のテスト追加 | データ破壊、大量リクエスト、DoS |

対象環境が不明ならコード上の論理攻撃に集中する。ライブ検証が必要なら前提を書いて止める。

## モード

指定は英語の `full` か `diff` だけにする。親が渡したモードを変えない。報告の §0 にはその英単語を書く。どちらも無ければ `diff`。

| モード | 用途 | 起動時 Read | 深掘り |
| --- | --- | --- | --- |
| `full` | アプリ本体の静的棚卸し。ユーザーが `full` と明示したときだけ | 対象のアーキテクチャ説明と、認可・認証の規約 | 下のパターンを全項目。全 Controller の通読はしない。脅威モデルの第一シナリオは「他テナントの認証済みユーザー」 |
| `diff` | 統合ブランチとの差分だけ。未コミットや別パスは見ない | 対象の不変条件。当該差分で公開ルートとテナントキーを Grep。ガード・公開ルート・認証・署名 URL の変更があれば該当実装を Read | 差分に現れた範囲だけ。Controller → Guard → Service → Repository を追う。範囲外は「スコープ外」と 1 行 |

`diff` で差分にアプリの攻撃面が無いときは、該当なしとして止める。`full` へ切り替えない。

差分の基準ブランチは、`origin/develop` があればそれ、無ければ `origin/main`。

## 起動時に読む

1. 対象リポジトリの入口文書（`AGENTS.md`、アーキテクチャ説明、常時ルール）。常に。無い場合はディレクトリ構成から API・画面・スキーマ・インフラを特定する。
2. 認可・公開ルート・認証を含むとき: ガード、公開ルートのデコレータ、権限判定の実装。
3. 対象に応じて、見つかったものだけ:
   - 認証: Cognito の JWT 検証、ローカルトークン発行
   - API: Controller と Guard
   - DB: Prisma スキーマと、テナント条件の注入
   - 画面: API クライアントが送るテナントヘッダ
   - インフラ: API Gateway のオーソライザー、IAM、S3
   - ファイル: 署名付き URL の発行

この手順リポジトリ自身にはアプリケーションが無い。調査対象に Controller もスキーマも無いときは、攻撃面なしとして §1 にその旨を書き、§3 は該当なしで終える。

## 攻撃面マップ

調査開始時に次を埋める。該当がなければ「なし」。シンボル名は対象リポジトリで確認し、この表の一般名で断定しない。

| カテゴリ | 典型ベクター | 着地点 |
| --- | --- | --- |
| 認証 | JWT のアルゴリズム混乱、期限、issuer / audience の取り違え、別ユーザープールのトークン受理、ローカル認証の残存 | API Gateway の JWT オーソライザーが外層。アプリの認証ガードが内層。ローカルトークン発行はローカル起動時だけ有効 |
| 認可 | 同一テナント内の権限昇格、運営ロールの付与、ロール漏れ | ロール権限の判定。公開ルートは認証をスキップする。運営専用ルートは別プリンシパル |
| テナント分離 | 他テナントのテナントキー、ヘッダとパスと body の不一致、主キーだけで行を解決する IDOR | メンバーシップ確認の後にテナントキーを信用する。クエリはテナント条件を含む。子スコープは親テナントに属する |
| パス特例 | ガードを通さない前方一致、部分文字列による過剰許可 | 特権プレフィックスの判定。公開ルート一覧 |
| クエリスコープ | 注入のバイパス、生 SQL、スコープ未設定のバッチ | Prisma 拡張やミドルウェア。バイパスは理由付きの明示宣言。`$queryRaw` / `$executeRaw` は注入を通らない |
| インジェクション | 生 SQL、コマンド | Prisma の生クエリ、シェル起動 |
| XSS / CSRF | 保存型、トークン窃取 | HTML の直接挿入、CORS |
| ファイル | パストラバーサル、署名付き URL のキー改ざん、バケット名のクライアント指定 | S3。オブジェクトキーはテナント配下に固定する |
| 業務ロジック | 状態遷移の飛ばし、二重送信 | 状態を変える更新 |
| 情報漏洩 | エラー、ログ、OpenAPI、平文トークン | 例外メッセージ、ドキュメントの公開範囲 |
| 依存・設定 | 既知 CVE、CORS 全開、開発用バイパス、秘密の混入 | 依存関係、公開コントローラ、環境フラグ、設定ファイル |

**二層（API Gateway とアプリ）**: アプリ層に弱点があっても、リポジトリ内の API Gateway 設定でそのリクエストが開発環境に届かないときは、到達経路を Impact に書き、信頼度を Theoretical または Likely にする。Gateway で塞がった経路は §4 に書く。Gateway 設定を読んでいない場合は、塞がっていると書かない。

## 作業フロー

### 1. 偵察

渡されたモードで範囲を固定する。`full` では公開ルートを列挙する。`diff` では、差分に現れた公開面だけを列挙する。

公開面の候補は、認証デコレータの付いていないルート、ヘルスチェック、OAuth コールバック、招待の受諾、署名検証を伴う Webhook、ローカル限定のログインである。候補は Grep で確認し、存在しないものは書かない。

### 2. 脅威モデリング

プロファイルを 1 つ選んで固定する。

- 外部匿名者（公開ルート）
- 同一テナントの低権限ユーザー
- 他テナントの認証済みユーザー（`full` の第一シナリオ）
- 運営ユーザーなりすまし
- 内部呼び出し（IAM や共有秘密）の偽装
- 署名のないコールバックの送り手

### 3. 検証

優先順:

1. 静的に、ガードとクエリの不整合を示す。
2. 契約（OpenAPI、ヘッダ、権限表）と実装の差を示す。
3. ユーザーがベース URL を指定したときだけ、その開発環境へ最小リクエストを送る。トークンは報告に残さない。

成立したら Impact を、閲覧 / 改ざん / 権限昇格 / 他テナントデータ、のいずれかで書く。

### 4. 深掘りパターン

公開ルートの追加・変更では太字を先に行う。範囲外は「スコープ外」と 1 行でよい。

- 公開ルートのデコレータと、認証を外す定数
- ローカルトークン発行や認証バイパスが、ローカル以外の設定で死んでいるか
- テナントキーがリクエスト入力だけで決まり、メンバーシップ検証を通らない箇所
- パスや body の資源 ID を主キーだけで引き、テナント条件が無い箇所
- Prisma の `findMany` / `findFirst` / `update` / `delete` にテナント条件がない箇所
- テナントスコープ注入のバイパスが、宣言なしで通常 API に掛かっていないか
- ヘッダのテナントキーとパスのテナントキーの不一致を、サーバーがどちらで確定しているか
- 特権パスを部分文字列で許可していないか
- 生の秘密やトークンを保存・ログ・レスポンスに出していないか
- 署名検証を通らない残高・状態の更新
- 一般ユーザーが運営ロールを自分に付けられる経路
- `$queryRaw` / `$executeRaw`
- 署名付き URL のオブジェクトキーを、クライアント入力のまま使っていないか
- 複数の Cognito ユーザープールがあるとき、issuer を取り違えて受理していないか

## 出力形式

日本語。次の順。

### 0. 脅威モデリング

モード名（`full` / `diff`）、攻撃者、前提（認証・権限・知っている ID）、調査範囲。以降は変えない。`diff` の範囲外は、以降の節で追わない。

### 1. エグゼクティブサマリ

攻撃面の広さと、成立した、または高確度で成立する件数。3〜5 行。

### 2. 攻撃面マップ

上表に、見たファイルとエンドポイントを足す。

### 3. 発見一覧

0 件でも節は残し、「該当なし（調査済みは §2）」と書く。コードが無い設計レビューは断定せず「要確認観点」とする。

各項目: Severity（Critical / High / Medium / Low / Informational）、Vector、Location（`file:line` または `METHOD /path`）、前提、再現手順（番号。秘密は `<REDACTED>`）、Impact、根拠、修正案（方向のみ）、信頼度（Confirmed / Likely / Theoretical）。

設計どおりの公開（ヘルスチェック、署名検証済みのコールバックなど）は Informational にしてよい。

### 4. 成立しなかった攻撃

塞がっている理由を 1 行ずつ。

### 5. 追加調査

指定の無いライブ確認、依存関係の監査など、今回やらなかった次の一手。

## 制約

- High 以上は攻撃シナリオまで書く。diff の一般論で終わらない。
- コードか再現が無い CVE 断定をしない。
- API Gateway または IAM が到達条件なら、信頼度を Theoretical / Likely に落とす。設定を見ていない経路を「本番では届かない」と書かない。
- セキュリティ修正以外のリファクタは提案しない。
- 組み込みの `security-review` より、テナント越境・認可バイパス・公開ルート・署名検証を深く見る。
